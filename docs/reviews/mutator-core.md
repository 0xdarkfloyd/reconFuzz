# Mutator Core Review

## 1. Structure map

### `Mutator.mutate()`

1. The constructor overlays caller configuration on the defaults, then validates both mutation probabilities before the object can be used. The defaults are 0.8 for AST mutation and 0.2 for Wasm mutation (`src/mutator/index.ts:17-30`).
2. `mutate()` first performs a shallow shape check: the input must be a non-null object, `javascript` must be a non-null object, and `wasm` must be an array; malformed input produces `TypeError` (`src/mutator/index.ts:34-45`).
3. The method starts with the input program and uses the injected RNG when present, otherwise `Math.random` (`src/mutator/index.ts:47-48`). The AST stage is gated by a non-empty mutator list and `astProbability`; it selects one mutator, calls it once, validates that the result is a Babel `File`, and replaces only `javascript` on success (`src/mutator/index.ts:50-62`).
4. The Wasm stage is independently gated by a non-empty mutator list, at least one module, and `wasmProbability`. It selects one Wasm mutator for the call and applies that same mutator to every module, validating each returned module's name and byte-array shape (`src/mutator/index.ts:70-90`). Thus one call can apply at most one AST mutator kind and one Wasm mutator kind, while the selected Wasm mutator may affect multiple modules (`src/mutator/index.ts:50-98`).
5. AST exceptions or invalid results are caught and leave the current JavaScript value in place; Wasm exceptions or invalid results are caught per module and return that module while mapping continues. A failed AST stage therefore does not prevent the Wasm stage, and one failed Wasm module does not prevent attempts on later modules (`src/mutator/index.ts:53-67`, `src/mutator/index.ts:78-98`).

### Probability validation and selection

`validateProbability` requires each configured probability to be a finite number in the inclusive range `[0, 1]` (`src/mutator/index.ts:116-120`). `pick` rejects an empty array and non-finite RNG samples, clamps other samples into `[0, 1)`, and maps the sample uniformly by array index when the RNG itself is uniform (`src/mutator/index.ts:104-114`). Probability gates call the RNG directly, whereas the later selection calls go through `pick` (`src/mutator/index.ts:50-51`, `src/mutator/index.ts:74-76`).

### Wasm mutators

`WASM_HEADER_SIZE` is eight bytes (`src/mutator/wasm-mutators.ts:6`). `bitFlip` clones the bytes, returns an unchanged clone when there is no byte after the header, and otherwise flips one randomly selected bit in one randomly selected post-header byte (`src/mutator/wasm-mutators.ts:18-30`). `truncateTail` also clones first, returns an unchanged clone for header-only or shorter input, and otherwise keeps between eight bytes and one byte fewer than the original (`src/mutator/wasm-mutators.ts:33-43`). `insertNop` copies the complete byte array into a one-byte-longer allocation and appends `0x01` (`src/mutator/wasm-mutators.ts:45-50`). All three preserve the existing first eight bytes: the first two explicitly exclude that range from mutation/removal, while the third only appends (`src/mutator/wasm-mutators.ts:22-28`, `src/mutator/wasm-mutators.ts:37-42`, `src/mutator/wasm-mutators.ts:46-49`).

### `minimizeProgram`

The minimizer copies the top-level statement array, scans it from the end, and tests candidates made by removing one statement at a time. A removal is committed only when the async predicate returns true; full passes repeat until no removal succeeds or `maxPasses` is reached (`src/mutator/minimizer.ts:36-57`). This is greedy single-statement deletion, not chunk-based delta debugging, and its reduction scope is only `program.javascript.program.body` (`src/mutator/minimizer.ts:24-28`, `src/mutator/minimizer.ts:36-55`). Candidate and final files retain the original directives, source type, interpreter, and file-level comments; non-JavaScript fields, including Wasm modules, are carried through unchanged by object spread (`src/mutator/minimizer.ts:24-34`, `src/mutator/minimizer.ts:46-49`, `src/mutator/minimizer.ts:59-62`).

## 2. Correctness & robustness

- **CONFIRMED — built-in clone discipline.** Each Wasm mutator allocates a fresh byte array before returning and does not write through `module.bytes`; even the short-input paths return the first clone (`src/mutator/wasm-mutators.ts:22-30`, `src/mutator/wasm-mutators.ts:37-42`, `src/mutator/wasm-mutators.ts:46-50`). The minimizer copies the body arrays before splicing, so it does not splice the input program's body array (`src/mutator/minimizer.ts:36`, `src/mutator/minimizer.ts:43-45`, `src/mutator/minimizer.ts:51-52`).
- **LIKELY — custom mutators must follow the same no-in-place-mutation contract.** The orchestrator passes the current AST and module objects directly to configured mutators and does not snapshot them before invocation (`src/mutator/index.ts:53-55`, `src/mutator/index.ts:80-82`). If a custom mutator changes its argument and then throws, returning the same AST/module reference in the catch path cannot restore the prior contents, so the stated failure isolation is conditional on mutation-by-copy (`src/mutator/index.ts:63-67`, `src/mutator/index.ts:91-95`).
- **CONFIRMED — normal mutator failures are isolated.** Thrown errors and invalid return shapes from an AST mutator are contained at the AST stage, and the equivalent Wasm handling is per module (`src/mutator/index.ts:54-67`, `src/mutator/index.ts:80-96`). Selection is outside those `try` blocks, however, so an error from `pick`, including a non-finite selection sample, propagates from `mutate()` rather than being isolated (`src/mutator/index.ts:51-54`, `src/mutator/index.ts:76-81`, `src/mutator/index.ts:104-113`).
- **CONFIRMED — probability configuration is robust, but probability samples are not validated.** Construction rejects missing, non-numeric, non-finite, or out-of-range probability values (`src/mutator/index.ts:27-30`, `src/mutator/index.ts:116-119`). The gate samples are compared directly, so a non-finite injected sample can silently skip or enter a stage before selection performs its own finite-value check (`src/mutator/index.ts:50-51`, `src/mutator/index.ts:74-76`, `src/mutator/index.ts:108-110`).
- **CONFIRMED — Wasm header bytes are protected.** Eligible mutation indices and truncation lengths start at byte eight, and append-only mutation leaves all prior bytes intact (`src/mutator/wasm-mutators.ts:6`, `src/mutator/wasm-mutators.ts:22-28`, `src/mutator/wasm-mutators.ts:37-42`, `src/mutator/wasm-mutators.ts:46-49`). Header preservation is byte-level only; none of these functions parses or validates Wasm sections (`src/mutator/wasm-mutators.ts:18-50`).
- **CONFIRMED — minimizer removals are predicate-gated.** Every proposed deletion is passed to the predicate and committed only on a truthy result (`src/mutator/minimizer.ts:43-54`). Predicate errors are not caught and therefore abort minimization (`src/mutator/minimizer.ts:51`).
- **CONFIRMED — predicate preservation has a caller precondition.** The original program is never passed to the predicate before reduction begins, so the function guarantees preservation only when the caller has already established that the input satisfies the predicate (`src/mutator/minimizer.ts:19-24`, `src/mutator/minimizer.ts:36-51`). If no candidate is accepted, the rebuilt input is returned regardless of its predicate result (`src/mutator/minimizer.ts:41-62`).
- **CONFIRMED — directives, file comments, and empty bodies are handled.** Every candidate and the final file are rebuilt with the original directives and file-level comments (`src/mutator/minimizer.ts:24-34`, `src/mutator/minimizer.ts:46-49`, `src/mutator/minimizer.ts:59-62`). The last remaining statement may be removed when the predicate accepts the empty candidate, and an initially empty body returns a valid rebuilt file without entering the inner loop (`src/mutator/minimizer.ts:36-45`, `src/mutator/minimizer.ts:51-62`).
- **SPECULATIVE — shallow node reuse may matter to callers that retain AST identities.** The minimizer clones arrays but reuses surviving statement, directive, comment, and interpreter objects in rebuilt files; this is efficient, but downstream mutation of a result could share nested objects with the input (`src/mutator/minimizer.ts:24-36`, `src/mutator/minimizer.ts:44-49`, `src/mutator/minimizer.ts:59-62`).

## 3. Effectiveness gaps

- **One AST mutator per call.** A successful probability gate performs exactly one selection and one invocation; there is no mutation budget or composition loop within the AST stage (`src/mutator/index.ts:50-62`).
- **First-match-only effect is not compensated at orchestration level.** The orchestrator invokes the selected AST mutator once and accepts its single returned `File`; it has no mechanism to request another matching site or continue after the selected mutator's first application. The internal match-selection policy is outside the three-file review scope (`src/mutator/index.ts:51-62`).
- **No mutator-level no-op detection or retry.** Valid return shape is the only acceptance test, so an unchanged AST, a short-module clone from `bitFlip`/`truncateTail`, or any same-content result consumes the attempt without selecting another mutator (`src/mutator/index.ts:55-62`, `src/mutator/index.ts:82-90`, `src/mutator/wasm-mutators.ts:22-23`, `src/mutator/wasm-mutators.ts:37-38`). The review brief states that the HTTP adapter retries, but that adapter is outside the permitted source set; `Mutator` itself contains no retry loop (`src/mutator/index.ts:34-102`).
- **The minimizer is disconnected within the reviewed core.** Its only occurrence in scope is the exported function definition; `Mutator` neither imports nor calls it, so minimization is library-only within these files and is not part of `mutate()` (`src/mutator/minimizer.ts:19-62`, `src/mutator/index.ts:4-7`, `src/mutator/index.ts:34-102`). The review brief identifies it as never called repository-wide; that broader call-site claim is not independently testable under the three-file restriction.
- **Reduction granularity is top-level JavaScript statements only.** Candidate generation only splices `origProgram.body`; it does not reduce expressions or nested statements, and the object spread preserves Wasm unchanged (`src/mutator/minimizer.ts:24-28`, `src/mutator/minimizer.ts:36-49`, `src/mutator/minimizer.ts:59-62`).
- **Wasm strategies are raw-byte only.** The three operations flip a post-header bit, truncate a suffix, or append one byte, with no decoding of sections, functions, instructions, indices, or encoded lengths (`src/mutator/wasm-mutators.ts:18-50`). Consequently, header preservation does not imply structurally coherent Wasm output (`src/mutator/wasm-mutators.ts:6`, `src/mutator/wasm-mutators.ts:22-28`, `src/mutator/wasm-mutators.ts:37-49`).

## 4. Prioritized improvement list

1. Add bounded no-op detection and alternate-mutator/site retries inside `Mutator`, because current shape-only acceptance can spend an iteration without changing program content (`src/mutator/index.ts:50-62`, `src/mutator/index.ts:76-98`).
2. Support configurable mutation budgets and AST mutator composition, because the current single invocation limits compound test-program variation (`src/mutator/index.ts:50-62`).
3. Add Wasm structure-aware operators backed by a decoder/encoder, because all current operators work on raw byte positions and cannot target semantic module elements (`src/mutator/wasm-mutators.ts:18-50`).
4. Expose mutation-site enumeration or retry metadata at the AST-mutator boundary, because a single call gives orchestration no way to move beyond a first or ineffective match (`src/mutator/index.ts:51-62`).
5. Integrate `minimizeProgram` into the result-processing workflow with explicit evaluation limits, because it is presently a standalone definition rather than part of the core mutation path (`src/mutator/minimizer.ts:19-23`, `src/mutator/index.ts:34-102`).
6. Extend reduction hierarchically to nested statements, expressions, and Wasm structures, because the current candidate builder removes only top-level JavaScript statements (`src/mutator/minimizer.ts:24-28`, `src/mutator/minimizer.ts:36-49`).
7. Enforce the mutation-by-copy contract and validate every RNG sample at one boundary, because in-place custom mutations and selection-time RNG errors can bypass the intended isolation behavior (`src/mutator/index.ts:50-55`, `src/mutator/index.ts:63-67`, `src/mutator/index.ts:76-82`, `src/mutator/index.ts:91-95`, `src/mutator/index.ts:104-113`).
